## 第一性原理

### 为什么需要多种语言？

**不同场景的最优解不同：**
- **研究探索**：开发速度最重要 → Python
- **实盘执行**：延迟和稳定性最重要 → C++ / Rust
- **数据管道**：吞吐量和并发最重要 → Go / Rust
- **风控计算**：正确性最重要 → 任何语言都可以，但要有严格测试

**核心原则：热路径用编译型语言，冷路径用解释型语言。**

### 选型决策树

```
这个组件在交易热路径上吗？
  ├─ 是（微秒/毫秒级延迟要求）
  │    └─ C++ / Rust
  └─ 否（秒级以上延迟）
       ├─ 需要快速迭代和数据分析？ → Python
       ├─ 需要高并发和网络服务？ → Go
       └─ 需要嵌入式/交易终端？ → MQL5 / C#
```

## 各语言角色与选型

### Python（研究层主力）

**定位**：策略研究、因子挖掘、回测验证、ML 训练

**优点**：
- 生态最丰富（Pandas、NumPy、scikit-learn、PyTorch）
- 开发速度快，迭代效率高
- 量化社区资源最多

**缺点**：
- 慢（解释型、GIL）
- 不适合高频实盘热路径
- 动态类型，大型项目维护成本高

**适用场景**：
- ✅ 策略研究和回测
- ✅ ML 模型训练
- ✅ 数据分析和可视化
- ❌ 高频交易执行
- ❌ 低延迟订单路由

### C++（执行层主力）

**定位**：实盘执行、低延迟热路径、订单管理

**优点**：
- 极快（编译型、零开销抽象）
- 精确控制内存和 CPU
- 生态成熟（Boost、Intel TBB）

**缺点**：
- 开发慢，学习曲线陡
- 内存管理复杂，容易出 bug
- 编译时间长

**适用场景**：
- ✅ 高频做市、低延迟交易
- ✅ 订单路由和执行算法
- ✅ FPGA 配套软件栈

### Rust（新兴选择）

**定位**：执行层新选择，兼顾性能和安全

**优点**：
- 接近 C++ 的性能
- 内存安全（无 GC）
- 现代工具链（cargo）
- 并发安全

**缺点**：
- 生态不如 C++ 成熟
- 学习曲线陡
- 量化社区采用率还不高

**适用场景**：
- ✅ 新一代交易系统的执行层
- ✅ 需要高并发的数据管道
- ⚠️ 还在快速发展中

### Go（数据管道与服务）

**定位**：中后台服务、数据管道、监控系统

**优点**：
- 开发效率高（语法简单）
- 原生并发（goroutine）
- 部署简单（静态编译）

**缺点**：
- 性能不如 C++/Rust
- 不适合数学计算密集型场景

**适用场景**：
- ✅ 数据采集和清洗管道
- ✅ OMS/EMS 后台服务
- ✅ 监控和告警系统

### MQL5（MT5 执行终端）

**定位**：MT5 平台的策略执行

**优点**：
- 直接对接 MT5，无需额外接口
- 内置回测和优化
- 与经纪商无缝对接

**缺点**：
- 生态封闭
- 性能有限
- 不适合复杂系统

**适用场景**：
- ✅ 零售外汇/黄金交易
- ✅ 小型策略的实盘执行
- ❌ 机构级大规模系统

## 代码架构最佳实践

### 分层架构

```
┌─────────────────────────┐
│       接口层 (API)       │  ← 对外接口（实盘/回测/研究）
├─────────────────────────┤
│       业务逻辑层         │  ← 策略、信号、组合构建
├─────────────────────────┤
│       数据服务层         │  ← 数据获取、清洗、特征计算
├─────────────────────────┤
│       基础设施层         │  ← 数据库、消息队列、缓存
└─────────────────────────┘
```

### 核心设计原则

1. **关注点分离**：策略逻辑和数据获取分开，不要混在一起
2. **依赖注入**：数据接口通过依赖注入传入，方便测试
3. **接口抽象**：对外暴露接口，内部实现可替换
4. **配置外置**：参数、阈值不要硬编码，放配置文件
5. **单一职责**：每个模块只做一件事

### 因果性保证（最重要）

**前视偏差是量化交易第一大死法。**

代码层面的保证：
- 所有特征计算只能使用 `available_at <= bar.close` 的数据
- 时间戳必须显式传递，不要隐式依赖"当前时间"
- 回测引擎必须逐 bar 推进，不能一次性计算所有结果
- 单元测试要验证：未来数据不能影响过去的计算

### 可审计性设计

每笔交易的决策都必须可还原：
- 记录：时间、标的、方向、仓位、信号来源、模型版本、参数
- 决策日志：为什么买/卖？各层输入是什么？
- 版本追踪：代码版本、数据版本、模型版本全部记录

## 测试与验证体系

### 测试金字塔

```
        /\
       /  \  E2E 测试（少量）
      /----\
     /      \  集成测试（中等）
    /--------\
   /          \  单元测试（大量）
  /------------\
```

### 各层测试内容

#### 单元测试
- 每个函数/模块单独测试
- 验证：输入 → 输出是否符合预期
- **关键测试**：前视守卫测试（确保不会用到未来数据）

#### 集成测试
- 多个模块组合测试
- 验证：数据 → 信号 → 订单 整条链路是否正确
- 关键测试：回测引擎的因果性验证

#### 回测验证（特殊测试）
- 样本外测试是唯一真理
- PBO + CPCV + Deflated Sharpe 三重验证
- 蒙特卡洛压力测试

### 黄金集测试

**定义**：一组精心挑选的测试用例，覆盖关键场景。
**规则**：
- 黄金集测试不得放宽断言
- 每次代码改动都要跑黄金集
- 失败必须修复，不能跳过

## CI/CD 与 MLOps

### CI/CD 流水线

```
代码提交 → 自动测试 → 代码审查 → 合并 → 自动部署
```

### MLOps 流水线

```
数据版本化 → 特征工程 → 模型训练 → 模型评估 → 模型注册 → 模型部署 → 监控衰减
```

### 关键实践

1. **数据版本化**：用 DVC 或类似工具管理数据版本
2. **实验跟踪**：MLflow / Weights & Biases 记录每次实验
3. **模型仓库**：统一管理模型版本
4. **自动化部署**：模型训练完成自动部署到实盘
5. **漂移监控**：监控数据分布和模型性能变化

## 性能优化指南

### Python 性能优化

1. **向量化**：用 NumPy/Pandas 的批量操作，不要写 for 循环
2. **Cython / Numba**：热点函数用 JIT 编译加速
3. **多进程**：CPU 密集型任务用 multiprocessing（注意 GIL）
4. **缓存**：重复计算的结果缓存起来
5. **延迟加载**：不要一次性加载所有数据

### C++ 性能优化

1. **零拷贝**：尽量减少内存拷贝
2. **预分配**：容器预分配大小，避免动态扩容
3. **缓存友好**：数据结构按内存布局设计
4. **无锁编程**：高并发场景用无锁数据结构
5. **性能剖析**：用 perf / VTune 找到热点

### 热路径优化原则

**不要过早优化。** 先 profiler，再优化。
**优化 20% 的代码，带来 80% 的性能提升。**

## 顶级机构工程实践

### 文艺复兴科技
- **研究与生产紧密耦合**：研究员直接写生产代码
- **极致的代码审查**：每行代码都要被多人审查
- **大量自动化测试**：黄金集测试覆盖关键路径

### Two Sigma
- **数据基建是护城河**：投入大量资源建数据管道
- **ML 驱动开发**：用 ML 辅助代码生成和调试
- **云原生**：研究在云上，弹性扩展

### Citadel Securities
- **极端低延迟**：FPGA + 内核旁路 + co-location
- **C++ 为主**：热路径全部用 C++ 写
- **微服务架构**：每个功能独立服务，故障隔离

### Millennium
- **Pod 自治**：每个 pod 自己选技术栈
- **共享中后台**：风控、运营、数据平台是集中的
- **平台化**：提供标准化工具，让 pod 专注策略

### 工程共识

1. **简单 > 复杂**：能简单写就不要复杂写
2. **测试 > 速度**：宁可慢一点，也要保证正确
3. **文档 > 记忆**：重要决策必须写下来
4. **可观测 > 可调试**：出问题能立刻看到，不要靠猜
5. **故障隔离 > 单点完美**：一个模块挂了，其他模块继续跑
