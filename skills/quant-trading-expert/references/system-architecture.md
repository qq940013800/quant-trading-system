## 第一性原理

### 一个交易系统到底在做什么？

```
数据输入 → 信号生成 → 组合构建 → 订单执行 → 风控监控 → 绩效分析
```

这是一个闭环：
- **输入**：行情数据、基本面数据、另类数据
- **决策**：用模型判断买什么、买多少
- **执行**：把订单送到交易所，尽量少付成本
- **风控**：确保不出事（不爆仓、不违规）
- **反馈**：分析结果，改进策略

### 为什么需要企业级架构？

**个人交易者**：一个 Python 脚本 + MT5 就够了。
**企业级系统**：需要支撑——
- 多策略并行（几十个策略同时跑）
- 多资产类别（股票、期货、期权、外汇、加密）
- 低延迟要求（微秒级到毫秒级）
- 严格风控（事前拦截、事中监控、事后审计）
- 高可用（99.99% 可用性，全年 downtime < 53 分钟）
- 可扩展（新策略上线不需要重写整个系统）

### 架构设计的第一性原则

1. **关注点分离**：研究、执行、风控是三个独立的职责，不能混在一起
2. **低延迟路径与研究路径物理分离**：热路径（交易执行）和冷路径（策略研究）是两套独立系统
3. **风控前置**：不是事后检查，是在订单发出之前就拦截
4. **一切可审计**：每笔交易的决策过程都能还原
5. **故障隔离**：一个策略出问题，不影响其他策略

## 数据层架构

### 第一性问题：数据层要解决什么？

1. **采集**：从各种数据源把数据拿进来
2. **清洗**：处理缺失值、异常值、时区对齐
3. **存储**：长期保存，支持快速查询
4. **分发**：把数据送到需要的地方（研究环境、实盘环境）

### 数据分类

| 数据类型 | 例子 | 更新频率 | 存储方式 |
|---------|------|---------|---------|
| **Tick 数据** | 逐笔成交、订单簿变化 | 实时（微秒级） | 时序数据库 + 压缩归档 |
| **K线数据** | 1分钟/5分钟/日线 | 分钟级 | 时序数据库 |
| **基本面数据** | 财报、PE/PB、营收 | 季度/日 | 关系数据库 |
| **另类数据** | 舆情、卫星、信用卡 | 日/周 | 对象存储 + 元数据索引 |
| **参考数据** | 合约规则、交易时间、产品参数 | 低频变更 | 配置中心 + 版本管理 |

### 时序数据库选型

| 数据库 | 优点 | 缺点 | 适用场景 |
|--------|------|------|---------|
| **ClickHouse** | 列式存储、查询极快、压缩比高 | 写入不如 InfluxDB | 大规模历史数据分析 |
| **QuestDB** | 高性能、低延迟、SQL 兼容 | 生态较新 | 实时行情存储 |
| **InfluxDB** | 生态成熟、易用 | 大规模查询慢 | 中小规模监控数据 |
| **Parquet + DuckDB** | 简单、低成本、列式压缩 | 不支持实时写入 | 离线研究、历史回测 |

### 数据质量原则

1. **数据血缘**：每一条数据都能追溯来源
2. **时区统一**：所有数据用 UTC 存储，展示时再转换
3. **前视守卫**：确保特征计算不会用到未来数据
4. **数据校验**：异常值检测、缺失值监控
5. **版本管理**：参考数据变更要有历史版本

## 研究层架构

### 第一性问题：研究层要做什么？

1. **因子挖掘**：找到有预测力的信号
2. **回测验证**：在历史数据上测试策略表现
3. **模型训练**：用 ML 方法优化信号
4. **实验管理**：记录每个实验的参数和结果，可复现

### 回测引擎的两种模式

#### 向量化回测
- 用 NumPy/Pandas 批量计算，速度快
- 适合：快速验证、因子筛选
- 缺点：不模拟真实订单流，结果偏乐观

#### 事件驱动回测
- 逐 tick/逐 bar 模拟真实交易流程
- 适合：精细策略、执行算法研究
- 优点：更接近真实，考虑滑点和冲击
- 缺点：慢

### 研究层的关键原则

1. **样本外测试是唯一真理**：回测好看不算数
2. **实验可复现**：随机种子、数据版本、参数全部记录
3. **决策规则冻结**：实验前定好规则，不允许事后调整
4. **trials 计数包含失败试验**：试了 100 次只报最好的 1 次，那是运气

## ML/MLOps 架构

### 第一性问题：ML 在系统中处于什么位置？

**ML 不是核心，是工具。** 它的作用是：
- 从大量弱特征中提取模式
- 优化基础信号的仓位（meta-labeling）
- 辅助风控（异常检测）
- 优化执行（算法交易）

### MLOps 流水线

```
数据采集 → 特征工程 → 模型训练 → 模型评估 → 模型部署 → 监控衰减
```

### 关键组件

| 组件 | 作用 |
|------|------|
| **Feature Store** | 统一特征定义，训练和线上用同一套特征 |
| **实验跟踪** | 记录每次训练的参数、指标、数据集版本 |
| **模型仓库** | 存储训练好的模型，版本管理 |
| **模型服务** | 把模型部署成 API，供实盘调用 |
| **漂移监控** | 监控数据分布和模型性能变化，预警衰减 |

### ML 部署的两种模式

#### 批量预测
- 每天/每小时跑一次模型，输出信号
- 适合：中频策略、日频调仓
- 优点：简单、稳定

#### 实时预测
- 实时接收行情，实时输出信号
- 适合：高频策略、做市
- 优点：低延迟
- 缺点：复杂、对稳定性要求高

### 模型衰减监控

**核心假设**：所有模型都会衰减。你需要：
1. **数据漂移监控**：特征分布是否和训练时不一样了
2. **性能衰减监控**：最近一段时间的预测准确率是否下降
3. **自动退役机制**：衰减超过阈值就自动下线

## 执行层架构

### 第一性问题：执行层要解决什么？

1. **订单管理 (OMS)**：记录所有订单和仓位状态
2. **执行管理 (EMS)**：把大订单拆成小单，优化执行
3. **执行算法**：TWAP、VWAP、POV、Implementation Shortfall
4. **订单路由**：把订单送到正确的交易所/经纪商

### 执行算法的目标

**不是"卖个好价钱"，是最小化总交易成本：**

```
总成本 = 买卖价差 + 市场冲击 + 时机风险
```

### 低延迟架构（高频场景）

```
行情接收 → 信号计算 → 订单生成 → 交易所
   ↑          ↑          ↑
 FPGA      FPGA       FPGA
 (微秒级)  (微秒级)   (微秒级)
```

关键技术：
- **FPGA 硬件加速**：硬件层面处理，比软件快 100 倍
- **内核旁路 (DPDK/Solarflare)**：绕过操作系统网络栈
- **co-location**：服务器放在交易所机房，物理距离最短
- **微波/激光链路**：比光纤快（光速在空气中比玻璃中快）

### 普通频率场景

不需要 FPGA，软件实现即可：
- C++ / Rust 写热路径
- 延迟目标：毫秒级（不是微秒级）
- 成本低很多

## 风控层架构

### 第一性问题：风控为什么是独立一层？

**因为风控不能信任策略。** 策略可能出错，模型可能失效，代码可能有 bug。风控是最后一道防线，必须独立。

### 三层风控体系

#### 事前风控（订单发出前拦截）
- 单笔订单限额（最大下单量）
- 仓位限额（单一标的最大持仓）
- 品种限额（单一品种总敞口）
- 资金限额（最大使用杠杆）
- 合规检查（交易时间、禁止交易品种）

#### 事中风控（实时监控）
- 实时盈亏监控（日亏限额）
- 实时仓位监控（预警线）
- 实时波动率监控
- 异常交易检测（突然大额下单）

#### 事后风控（每日/每周复盘）
- 回撤分析
- 风险归因
- 限额使用率报告
- 合规审计追踪

### 风控的关键原则

1. **风控前置**：不是事后检查，是订单发出前就拦截
2. **独立于策略**：风控系统不接受策略层的指令，只执行规则
3. **故障安全**：风控系统出问题时，默认拒绝交易（fail-safe）
4. **一切可审计**：每笔拦截和放行都有日志

## 高可用与灾备

### 可用性目标

| 级别 | 可用性 | 年度 downtime |
|------|--------|--------------|
| 普通系统 | 99.9% | 8.7 小时 |
| 交易系统 | 99.99% | 53 分钟 |
| 高频交易 | 99.999% | 5.3 分钟 |

### 高可用设计

1. **冗余部署**：关键服务至少 2 个实例，主备切换
2. **故障自动转移**：主节点挂了，备节点自动接管
3. **数据备份**：每日备份，异地备份
4. **降级策略**：部分功能出问题，核心交易功能仍然可用

### RTO / RPO

- **RTO（恢复时间目标）**：出事后多久能恢复？目标 < 5 分钟
- **RPO（恢复点目标）**：最多容忍丢多少数据？目标 ≈ 0（实时同步）

### 灾备方案

- **同城双活**：两个机房距离 < 50km，实时同步
- **异地灾备**：另一个城市的备份机房，异步复制
- **数据零丢失**：关键数据多副本同步写入

## 顶级机构架构实践

### 文艺复兴科技
- **海量弱信号叠加**：不是靠一个强 Alpha，是几千个弱信号叠加
- **极度防过拟合**：最严格的样本外测试流程
- **研究与生产紧密耦合**：研究员直接参与部署，不是写完论文就完事

### Two Sigma
- **数据基建是护城河**：不是策略本身，是快速验证策略的能力
- **ML 驱动研究**：用 ML 自动挖掘因子
- **云原生 + 混合架构**：研究在云上，实盘在本地

### Citadel Securities
- **做市为核心**：系统围绕做市场景优化
- **极端低延迟**：FPGA + co-location + 微波链路
- **库存管理是核心**：实时风险定价和库存动态调整

### Millennium
- **Pod 结构**：200+ 个独立小组，各自管理自己的策略
- **共享中后台**：风控、运营、技术平台是集中的
- **风险预算制**：每个 pod 有独立的风险限额，亏到线就降仓

### 架构设计的共识与分歧

**所有顶级机构都认同：**
- 研究和执行是分离的
- 风控是独立的、前置的
- 数据质量优先于模型复杂度
- 高可用是必须的

**不同机构的差异：**
- 高频做市派：极致低延迟，FPGA + 硬件加速
- 因子投资派：大数据 + ML 研究，延迟要求不高
- 多策略平台派：模块化、可插拔，支持多种策略

**核心教训**：没有"最优架构"，只有"最适合你策略类型和规模的架构"。
