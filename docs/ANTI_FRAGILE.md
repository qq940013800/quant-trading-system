# 反脆弱与逆向避坑手册

> 方法论说明：
> - **芒格逆向思维**："如果我知道自己会死在哪里，我就永远不去那个地方。"——本手册不罗列"怎么赚钱"，只罗列"怎么死"。
> - **塔勒布反脆弱**：系统要能从波动、压力、错误中获益，而不是被一次黑天鹅摧毁。反脆弱 ≠ 抗压，而是每次被打之后变得更强。
> - **诚实标注**：下文每条末尾若写【行业共识】，代表量化圈公开文献与头部机构普遍承认的死法；若写【本项目推测】，代表基于 `D:\Trader` 当前架构（Python 研究层 + MQL5 执行层 + WebSocket + OKX 对接中）推断出的特定风险，尚未在实盘验证。
> - **防御落点约定**：所有防御措施必须收敛到 `AGENTS.md` 已有的 11 条硬规则、目录边界与现有测试文件，不另起炉灶。

## 一、系统必死清单（20 条）

### A. 数据与前视类

#### 死法 1：特征里偷看了下一根 K 线
- **怎么发生**：写特征时用了 `df.shift(-1)`、用了整段均值/标准差（rolling 窗口对齐错误）、或者用 `loc[bar_index]` 取到了尚未收盘的 bar。回测曲线漂亮得不正常，实盘第一周就亏光。【行业共识】
- **代价量级**：回测夏普 3.0 → 实盘夏普 -0.5；单次爆仓或 30%+ 回撤，因为信号本身就是错的。
- **防御措施**：
  - `AGENTS.md` 硬规则 1（前视守卫）+ 硬规则 5（intra-bar 只允许已收盘 bar）。
  - 特征层：`core/features/base.py`、`core/features/regime.py`、`core/features/volatility.py` 所有 rolling/shift 必须显式写 `closed='right'` 语义。
  - 测试兜底：`tests/test_features_causal.py`、`tests/test_features_regime.py`——任何新特征必须在该文件追加断言，不得放宽（硬规则 10）。
  - 数据入口：`core/data/bar.py`、`core/data/loader.py` 强制按 `available_at <= bar.close` 切窗。
- **预警信号**：
  - 某个特征在回测里与下一根 bar 收益的相关系数异常高（>0.15 就该警觉）。
  - 夏普 > 2.5 且最大回撤 < 5%——大概率是前视而不是真本事。
  - 特征代码里出现 `shift(-`、`future`、`iloc[i+1]`、`iloc[i:]` 这类写法。

#### 死法 2：静默集泄漏——用"看不见的数据"偷偷调参
- **怎么发生**：CLEAN/KNOWN/静默集三分（见 `docs/data_splits.md`）。研究者嘴上说"没看静默集"，实际上：(a) 把静默集回测结果贴在了群里；(b) 因为静默集表现差，回头改了一个特征；(c) 模型训练时 `random_state` 变了导致验证集混入静默集样本。等正式上实盘，才发现静默集才是未来真实分布。【行业共识】
- **代价量级**：假性过拟合，回测到实盘衰减 80% 以上；这是量化基金注销的第一大死因。
- **防御措施**：
  - `AGENTS.md` 目录边界：**禁止读静默集数据**；硬规则 2（ATR/vol/Hurst 只在 CLEAN 估计，供需区只用 KNOWN 构建）。
  - 阈值校准脚本 `scripts/calibrate_regime.py --mode distribution` 默认不看 PnL，只看分布形状——从流程上杜绝"看结果调阈值"。
  - 缺口清洗产物 `experiments/gate_XAUUSD.yaml` 必须经人工审核才能进 `configs/`（目录边界）。
  - 测试：`tests/test_data_synthetic.py`、`tests/test_backtest_engine.py` 里加 split 边界断言。
- **预警信号**：
  - 研究者开始说"我只是看一眼静默集确认下方向"。
  - `configs/` 里某个 yaml 最近改了，但 `experiments/` 里没有对应 gate 文件。
  - 模型交叉验证得分波动 > 10% 而没改代码——说明切分种子在漂。

#### 死法 3：MT5 服务器时间与 Python 端时区错位
- **怎么发生**：MT5 经纪商服务器通常是 EET/EEST（UTC+2/+3），Python 端默认本地时间 UTC+8，或者容器里 UTC。`--tz` 参数没传、传错、或者代码里硬编码了"早上 8 点开盘"。结果：信号在错误的 bar 上触发，止损挂在了错的价位，隔夜持仓跨越了根本不存在的"交易日"。【行业共识 + 本项目推测】
- **代价量级**：单笔订单方向错误或触发时点偏移 2-8 小时；杠杆品种上一次就能吃掉一周利润。
- **防御措施**：
  - `AGENTS.md` 硬规则 6：MT5 服务器偏移必须与 Python 端 `--tz` 一致，**禁止硬编码**。
  - 时区工具：`core/data/timezone.py`；测试：`tests/test_data_timezone.py`——任何涉及时间对齐的改动必须跑这个文件。
  - MQL5 侧：`mt5/` 目录下的常量需人工确认才能改（目录边界），不允许脚本自行写入。
- **预警信号**：
  - Python 日志里 bar 时间与 MT5 终端图表上同一根 bar 时间戳差 2 小时以上。
  - 周末/节假日前持仓莫名被平掉。
  - 容器重启后信号时间整体平移。

#### 死法 4：数据缺口被静默填充成"假行情"
- **怎么发生**：XAUUSD 周末停盘、经纪商维护、WebSocket 断连 30 分钟，数据 loader 用 `ffill` 或前值填充，把这段空白当成"价格没动"。回测里这段时间没有波动，波动率被低估，止损被设得太窄；实盘开盘瞬间跳空直接打穿。【行业共识】
- **代价量级**：滑点放大 5-10 倍；跳空缺口一次亏 2-5R。
- **防御措施**：
  - 缺口清洗脚本 `core/gap_normalizer.py --sym XAUUSD --data data/XAUUSD_M5.csv --out experiments/gate_XAUUSD.yaml`（AGENTS.md 命令段）。
  - `core/data/validator.py`、`core/data/splits.py` 负责缺口标记；CLEAN 集定义本身就排除缺口段（硬规则 2）。
  - 测试：`tests/test_data_loader.py` 里加缺口段断言。
- **预警信号**：
  - 回测里出现连续 20 根以上一字线（high=low=close）。
  - 波动率指标在周末前后异常低。
  - 实盘开盘第一根 bar 振幅 > 平时 3 倍。

### B. 过拟合与研究流程类

#### 死法 5：网格搜索出的阈值被当成"上帝常数"
- **怎么发生**：在历史数据上扫 ATR 倍数 1.5/2.0/2.5/3.0，选夏普最高的那个，写死进 config。这不是阈值，这是对历史曲线的拟合。PBO（Probability of Backtest Overfitting）一旦 > 0.5，策略就是个精致的噪声。【行业共识】
- **代价量级**：样本内夏普 2.0，样本外 0.3；6-12 个月内自然失效。
- **防御措施**：
  - `AGENTS.md` 三不变量第 3 条：**阈值来自分布，不由绩效网格搜索产生**；硬规则 2（分布估计只用 CLEAN 集）。
  - `scripts/calibrate_regime.py --mode distribution`——阈值取分布分位数（如 20%/80%），不取绩效最优点。
  - 实验登记：`run_gate_experiment.sh --registry registry.yaml --variant <v> --mode dryrun`，`decision_rule` 必须在实验前冻结（硬规则 11）。
  - 测试：`tests/test_models_cv.py`、`tests/test_models_walkforward.py`、`tests/test_gatekeeper.py`。
- **预警信号**：
  - config 里某个阈值小数点后两位"刚好"是最优解。
  - 改了一个阈值，样本内曲线显著变好看，但 walk-forward 没重跑。
  - PBO 值（若计算）超过 0.3。

#### 死法 6：多重检验——试了 100 个策略挑最好的那个
- **怎么发生**：团队一个月跑了 80 个变体，挑夏普最高的报奖。没有 Bonferroni/FDR 校正，没有 deflated Sharpe ratio。那个"最好"的策略本质上是 80 次抛硬币里正面最多的那一次。【行业共识】
- **代价量级**：假性发现率 > 50%；实盘 3 个月内死亡。
- **防御措施**：
  - `registry.yaml` 的 `trials_N` 只能由实验脚本原子递增（含失败/中止），只增不减（硬规则 11）——让"试了多少次"成为公开账本，无法挑选。
  - 禁止手工改 `registry.yaml`（目录边界 + 硬规则 11）。
  - 报告层：`reports/` 里每个策略必须披露 `trials_N` 和 walk-forward 衰减比。
  - 测试：`tests/test_registry/`、`tests/test_agent_config.py`。
- **预警信号**：
  - 汇报 PPT 里只展示一个"明星策略"，不展示同期失败的 79 个。
  - `trials_N` 与实际实验脚本调用次数对不上。
  - 策略命名带 v27、v43 这种版本号，但没有对应 git commit。

#### 死法 7：样本外太短，把噪声当信号
- **怎么发生**：walk-forward 窗口只有 6 个月，切 4 段就觉得"样本外验证完毕"。金融时序的自相关性和非平稳性意味着 6 个月样本外的 t 统计量严重失真。【行业共识】
- **代价量级**：策略在未来 1-2 年内随机表现，团队却基于它加了杠杆。
- **防御措施**：
  - `scripts/run_walkforward.py`——窗口长度、滚动步长必须显式配置，禁止默认 6 个月。
  - `core/models/walkforward` 相关测试 `tests/test_models_walkforward.py`。
  - 决策纪律：样本外 < 2 年、或 walk-forward 段数 < 8，不允许进入小资金阶段（见第二部分杠铃策略）。
  - 报告：`reports/` 必须披露 OOS 夏普的 t 值与置信区间。
- **预警信号**：
  - OOS 夏普的标准误 > 夏普本身。
  - 4 段 walk-forward 里 3 段赚钱 1 段巨亏，平均下来还行——中位数策略才是真策略。
  - 有人说"最近半年表现好，可以上了"。

#### 死法 8：L3 触发结果反哺 L1 位置定义（因果顺序被打破）
- **怎么发生**：五层架构本意是 L1 位置 → L2 状态 → L3 触发单向流动。但研究者发现"某个供需区被打穿后反而反转更猛"，于是回头把这个供需区的定义改成"被打穿 0.5 ATR 的那个区"。这是用 L3 的结果重新定义 L1，未来函数的变种。【行业共识 + 本项目推测】
- **代价量级**：和死法 1 同级——策略看起来有效，实盘失效。
- **防御措施**：
  - `AGENTS.md` 硬规则 3：L1 位置 → L2 状态 → L3 触发；**禁止 L3 结果反哺 L1 定义**。
  - 集合分离（硬规则 2）：供需区只用 KNOWN 集构建，不看后续是否盈利。
  - 架构层：`core/features/structure.py`（供需区）与 `core/models/ml_trend_strategy.py`（触发）之间通过显式接口传值，不允许反向回调。
  - 评审：任何修改 `structure.py` 的 PR 必须在描述里说明"这是 L1 定义调整，未参考 L3 结果"。
- **预警信号**：
  - 供需区定义里出现"如果…则…"这种条件分支。
  - `structure.py` import 了 `models/` 或 `execution/` 的东西。
  - 研究者说"我们优化了一下进场位置定义"——先问他看没看过该位置后续的盈亏。

### C. 执行与风控类

#### 死法 9：回测假设零滑点/固定 1 pip 滑点，实盘被流动性教育
- **怎么发生**：回测引擎里 `slippage = 0` 或固定 1 pip。实盘在非农、FOMC、API 限流时滑点 10-50 pip。策略胜率 55% 本来够覆盖成本，实盘变成 45%。【行业共识】
- **代价量级**：单笔成本 3-10 倍放大；高频/小利润策略直接变亏损。
- **防御措施**：
  - 回测成本模型：`tests/test_backtest_costs.py`——成本参数必须显式，禁止默认 0。
  - `core/execution/engine.py` 实盘与回测共用同一套成本函数，不允许回测一套、实盘一套。
  - 小资金阶段记录真实滑点分布，回填到 `experiments/` 作为下次回测参数。
  - 目录边界：`configs/` 下的成本参数需人工审核。
- **预警信号**：
  - 回测夏普与实盘夏普差 > 1.0。
  - 平均持仓时间 < 5 分钟，但回测没算手续费+滑点。
  - 大额订单的成交均价与下单时中间价差 > 5 倍历史假设。

#### 死法 10：止损被插针扫掉，或止损方向被错误移动
- **怎么发生**：(a) 止损放在 obvious level（整数关口、前低），被高频猎杀扫掉后反弹；(b) MQL5 代码里 PositionModify 把止损往亏损方向移了（"再等等看"）；(c) 用入场后的浮动 ATR 重新算止损，导致 R 倍数基准漂移。【行业共识】
- **代价量级**：胜率被人为压低 10-20%；一次"再等等"可能吃掉全月利润。
- **防御措施**：
  - `AGENTS.md` 硬规则 4：**止损只允许向盈利方向移动**；R 倍数用入场冻结的 `atr0/entryDist`。
  - 风控模块：`core/risk/stops.py`、`core/risk/sizing.py`；测试：`tests/test_risk_stops.py`、`tests/test_risk_sizing.py`——黄金集断言不得放宽（硬规则 10）。
  - `mt5/` 下的风控阈值常量禁止脚本修改（目录边界）。
- **预警信号**：
  - 持仓记录里止损价出现过"先远后近再更远"的锯齿。
  - 实盘止损被触发后 5 分钟内价格回到原方向——说明止损位在 obvious level。
  - R 倍数计算脚本里引用了动态 ATR 而不是 `atr0`。

#### 死法 11：OrderSend / PositionModify 异步返回值没检查
- **怎么发生**：MQL5 里 `OrderSend` 返回 1 只是"请求已提交"，真正成交要等 `ResultRetcode` 与 deal history。代码里 `if (OrderSend(...)) { update_position_state(); }`，结果请求被拒（requotes、保证金不足、市场关闭），本地状态却以为仓位已开。下一根 bar 信号来时基于错误状态再下一单。【行业共识】
- **代价量级**：重复开仓、对冲自成交、幽灵持仓；极端情况下净敞口翻倍。
- **防御措施**：
  - `AGENTS.md` 硬规则 7：异步返回必须检查返回值并重试。
  - `core/execution/engine.py` 与 `mt5/` 桥接层必须以 deal history 为准，不以 send 返回值为准。
  - 测试：`tests/test_execution_audit.py`、`tests/test_integration_bridge.py`、`tests/test_audit_replay.py`——每笔接受/拒绝可还原（三不变量第 2 条"决策可审计"）。
- **预警信号**：
  - 本地持仓表与 MT5 终端持仓偶尔对不上。
  - 订单 retcode 出现 10004/10006/10021 之类但日志里没有重试记录。
  - 同一标的在 1 秒内出现两个方向相反的仓位。

#### 死法 12：硬编码点值、手数、阈值
- **怎么发生**：代码里写 `double lot = 0.1;`、`double point = 0.01;`、`if (rsi < 30)`。换标的、换 broker、或 RSI 参数该调时，没人敢动也没人知道在哪动。【行业共识】
- **代价量级**：跨标的移植失败；改参数要翻遍整个 mt5/ 目录；一次手数配置错误 = 爆仓。
- **防御措施**：
  - `AGENTS.md` 硬规则 8：禁止硬编码点值/手数/阈值；走 `SymbolInfo*` 与 config。
  - 手数与仓位由 `core/risk/sizing.py` 统一计算，配置走 `configs/`（需人工审核）。
  - 测试：`tests/test_enum_mapping.py`、`tests/test_agent_config.py`。
- **预警信号**：
  - 代码评审时看到 magic number。
  - 换标的后系统跑起来手数不对。
  - config 文件里出现"XAUUSD专用"硬编码段。

### D. 系统可靠性类

#### 死法 13：WebSocket 断连没重连，行情冻结但系统以为还在跑
- **怎么发生**：WebSocket 实时通道（当前在建）断了之后没心跳、没指数退避重连、没有 stale 检测。最后一根 bar 是 30 分钟前的，但策略循环还在基于它发信号。订单在真实市场里被打到止损，本地却以为仓位还在。【本项目推测——架构当前在建，未实盘验证】
- **代价量级**：幽灵信号 + 幽灵持仓；一次断连 1 小时 = 可能错过止损/止盈，也可能在错误价位加仓。
- **防御措施**：
  - 心跳 + stale 检测：行情时间戳 > N 秒未更新，触发 `core/risk/circuit.py` 熔断器（参考现有 `circuit.py`）。
  - 测试：`tests/test_monitoring/`、`tests/test_risk_circuit.py`。
  - 告警：`docs/MONITORING_ALERTING.md` 定义断连告警阈值。
  - 纪律：任何"行情正常"的判断必须基于时间戳新鲜度，不基于"最后一条消息是成功的"。
- **预警信号**：
  - 日志里最后一条行情消息时间与当前时间差 > 30 秒但无告警。
  - 策略循环输出的 bar 时间戳不再前进。
  - 网络恢复后系统一次性补回大量延迟信号（未做去重）。

#### 死法 14：单点依赖——单 broker / 单数据源 / 单机 Docker
- **怎么发生**：所有钱放在一个 MT5 账户，所有行情来自一个 OKX WebSocket，所有进程跑在一台 docker-compose 里。broker 出金冻结、API key 被风控、宿主机重启——系统整体归零，没有任何降级路径。【行业共识】
- **代价量级**：流动性冻结期间无法止损；单点故障 = 全仓风险。
- **防御措施**：
  - 可选项思维（见第二部分）：`backend_api_python/` 与 `mcp_server/` 设计上预留多 broker 适配器接口。
  - Docker 编排：`docker-compose.yml`、`docker-compose.production.yml` 分离；`docs/deployment/` 记录部署拓扑。
  - 密钥：`secrets/` 目录禁止读/改（目录边界），OKX key 轮换流程写在 `docs/`。
  - 演练：每季度一次"拔掉 OKX 网线"演练，看系统是否自动切到备用数据源或进入只平仓不开仓模式。
- **预警信号**：
  - 架构图上所有箭头都汇聚到一个方框。
  - 没有第二个 broker 的模拟账户。
  - 团队说"我们从来没断过"——这就是要断的前兆。

#### 死法 15：`except Exception: pass` 把错误吞了
- **怎么发生**：Python 里写 `try: xxx\nexcept: pass`，MQL5 里写 `catch{}`。网络抖动、数据格式变化、权限错误全部被静默。三个月后对账发现少了 200 笔交易。【行业共识】
- **代价量级**：静默数据丢失；审计链断裂；三不变量第 2 条"决策可审计"直接破功。
- **防御措施**：
  - `AGENTS.md` 硬规则 9：**禁止 `except Exception: pass`；异常必须带上下文记录**。
  - 错误模块：`core/errors.py`。
  - 测试：`tests/test_errors.py`、`tests/test_audit_record.py`。
  - lint：mypy/pytest 配置（`mypy.ini`、`pytest.ini`）里把裸 except 列为错误。
- **预警信号**：
  - grep 代码库出现 `except:` 或 `except Exception:` 后紧跟 `pass`。
  - 日志里 ERROR 级别条数 = 0 但业务异常率 > 0。
  - 对账差异需要靠"重跑一遍"才能发现。

#### 死法 16：时钟漂移——宿主机 NTP 未同步，intra-bar 误触发
- **怎么发生**：容器/VM 时钟比真实时间慢 2-5 秒，intra-bar 逻辑（硬规则 5）基于本地 clock 判断"bar 已收盘"，其实交易所端那根 bar 还没收盘。信号提前发出，成为下一根 bar 的反向信号。【本项目推测——容器化部署特有】
- **代价量级**：信号提前/滞后几秒；高频策略上足以把夏普打对折。
- **防御措施**：
  - 硬规则 5（intra-bar 只允许已收盘 bar）+ 硬规则 6（时区一致性）。
  - 容器启动时校验 NTP 偏移，> 500ms 拒绝启动。
  - 信号触发时间戳同时记录 wall clock 与 exchange timestamp，差异 > 阈值时告警。
- **预警信号**：
  - `docker exec` 进容器 `date` 与宿主机不一致。
  - 同一信号在不同机器上触发时间差 > 1 秒。
  - 回测与实盘在边界 bar（如 15:59:59）上的决策不一致。

### E. 心理与纪律类

#### 死法 17：连亏后加仓——报复性交易
- **怎么发生**：连亏 5 笔后，手数悄悄从 0.1 调到 0.3，"一把回本"。这是最古老的死法，也是爆仓最快的路径。【行业共识】
- **代价量级**：单笔亏损放大 3 倍；5 笔连亏后第 6 笔直接爆仓。
- **防御措施**：
  - 仓位由 `core/risk/sizing.py` 统一计算，**手数不允许在交易循环里动态修改**。
  - 连亏熔断：`core/risk/circuit.py`——连续 N 笔亏损自动降仓位/停手。
  - 测试：`tests/test_risk_sizing.py`、`tests/test_risk_circuit.py`。
  - 纪律：人在连亏当天不允许改 config（改 config 需人工审核 + 次日生效）。
- **预警信号**：
  - 订单历史里手数分布出现"越亏越大"的趋势。
  - 交易员日志里出现"最后一笔"、"回本"、"没办法了"。
  - circuit breaker 被人为 bypass。

#### 死法 18：手工改 registry.yaml / 改阈值追溯历史
- **怎么发生**：策略表现差，研究者直接编辑 `registry.yaml` 把 `trials_N` 改小，或把历史阈值改成"现在的最优值"再跑一次回测。账本被污染，后续所有统计都失效。【行业共识 + 本项目推测】
- **代价量级**：审计链断裂；团队再也无法相信任何回测数字。
- **防御措施**：
  - `AGENTS.md` 硬规则 11：`trials_N` 只能由实验脚本原子递增，**禁止手工改写 `registry.yaml`**。
  - 目录边界：`registry.yaml` 需人工确认才可改。
  - 每次实验脚本调用 `run_gate_experiment.sh` 自动追加一行，含 git commit hash、时间、decision_rule。
  - 测试：`tests/test_registry/`。
- **预警信号**：
  - `git log registry.yaml` 里出现非实验脚本的 commit。
  - `trials_N` 与实际失败实验次数对不上。
  - 有人说"这个回测数字是干净的"——先查 registry。

#### 死法 19：OOS 表现好就盲目加杠杆
- **怎么发生**：样本外 3 个月夏普 2.0，团队激动地把仓位从 1% 提到 5%。3 个月太短，这 2.0 可能只是 regime 顺风。杠杆放大后，regime 一切换就爆。【行业共识】
- **代价量级**：5 倍仓位 = 一次 20% 的策略回撤变成账户 100%。
- **防御措施**：
  - 杠铃策略（见第二部分）：稳健底层仓位永远 ≤ 2%，探索仓位单独核算。
  - `core/risk/dynamic_allocator.py`——仓位上限基于 CLEAN 集估计的最坏回撤，不基于最近 3 个月表现。
  - 测试：`tests/test_dynamic_allocator.py`。
  - 纪律：加杠杆必须等 OOS ≥ 2 年 + 通过 PBO/CPCV 检验。
- **预警信号**：
  - 仓位调整理由引用了"最近 3 个月表现"。
  - 杠杆倍数与历史最长回撤不匹配。
  - 团队说"这次不一样"。

#### 死法 20：连赢后放松风控——跳过 dryrun 直接上实盘
- **怎么发生**：连赢 10 笔后，觉得策略成熟了，新版本跳过 dryrun / 影子模式，直接挂实盘。新版本有个未发现的前视 bug，第一周亏掉一个月利润。【行业共识】
- **代价量级**：新版本风险 = 未知；一次未测试的上线 = 全部历史利润。
- **防御措施**：
  - 强制流程：`run_gate_experiment.sh --mode dryrun` → 影子模式（与实盘并行但不下单）≥ 2 周 → 小资金（≤ 1% 仓位）≥ 1 个月 → 正常仓位。
  - 目录边界：`runtime/` 禁止改（运行态不可篡改）。
  - `docs/` 记录每个版本的上线阶段与回滚点。
  - 评审：任何跳过流程的上线申请，PR 必须 block。
- **预警信号**：
  - 发版说明里写着"紧急修复，直接上实盘"。
  - 影子模式运行 < 2 周就切换。
  - 交易员说"这个改动很小，不用测了"。

## 二、反脆弱设计：如何从波动中受益

> 防御 20 处死法是"不被打死"，反脆弱是"被打之后更强"。以下四条是本项目的主动设计。

### 2.1 杠铃策略：稳健底层 + 少量高风险探索
- **底层（90% 资金）**：只跑经过 OOS ≥ 2 年、PBO < 0.3、通过全部 20 死法检查的成熟策略；单标的仓位 ≤ 1%，组合层面日回撤熔断 ≤ 3%。
- **探索（10% 资金）**：专门给 AI/ML 新策略、新数据源、新 broker 做实验。亏完即止，不补仓。
- **本项目落点**：
  - `core/risk/dynamic_allocator.py` 把"底层/探索"两个池子分开计算，不允许探索池亏损传导到底层池。
  - 探索池的策略版本号必须带 `exp/` 前缀，与生产策略在 `registry.yaml` 里分账。
  - **关键纪律**：探索池的成功案例必须完整走完死法 20 的四阶段流程，才能"毕业"到底层池——不允许因为最近赚了钱就直升。
- **为什么反脆弱**：底层保证不死，探索池的每次失败都是便宜的学费；探索池偶尔跑出一个真策略，就升级成底层。波动（探索池亏损）是系统的养料而不是毒药。

### 2.2 压力测试 / 混沌工程清单
每月主动制造一次故障，观察系统是否按设计响应。**没出过错的系统不可信**。

| 故障注入 | 预期响应 | 验证文件 |
|---|---|---|
| kill 掉 WebSocket 进程 | 5 秒内 stale 告警，circuit breaker 触发只平仓不开仓 | `core/risk/circuit.py`、`tests/test_risk_circuit.py` |
| 拔掉 OKX 网线 30 分钟 | 订单流挂起，本地状态冻结；恢复后重放不重复下单 | `core/execution/engine.py`、`tests/test_execution_audit.py` |
| 喂入跳空 50 pip 的脏 bar | 缺口清洗器标记，不触发信号；日志 ERROR | `core/gap_normalizer.py`、`core/data/validator.py` |
| 手动把容器时钟拨慢 5 秒 | 启动时拒绝，或 intra-bar 逻辑拒绝触发 | 硬规则 5/6 |
| 构造一个 `except: pass` 的故障路径 | lint 失败 / pytest 失败 | `core/errors.py`、`tests/test_errors.py` |
| 模拟 broker 返回 requote | 重试 N 次后放弃，本地状态不更新 | 硬规则 7 |
| 磁盘写满 | runtime 日志停止但交易逻辑进入只读模式，不崩溃 | `runtime/` 目录边界 |

- **记录要求**：每次混沌演练写一份 `reports/chaos_YYYYMMDD.md`，记录实际响应 vs 预期响应的差距——差距就是下次要修的 bug。

### 2.3 可选项思维：保留多套数据源 / 多 broker / 多策略
- 塔勒布："不要把所有鸡蛋放在一个篮子里，但要保留多个篮子的接入能力。"
- **本项目落点**：
  - 数据源：`core/data/loader.py` 抽象统一接口，OKX / MT5 / 第三方数据商可插拔；切换数据源不需要改策略代码。
  - broker：`mt5/` 与未来 OKX 实盘走同一套 `execution/engine.py` 接口；第二个 broker 的模拟账户永远保持有资金、有连接。
  - 策略：底层池至少跑 2 个低相关性策略（一个趋势、一个均值回归），避免单一策略 regime 失效时全仓暴露。
  - **关键**：保留可选项本身有成本（第二个 broker 要存保证金），但这个成本是"保险费"，不是浪费。

### 2.4 失败成本压到最低：dryrun / 影子 / 小资金
- 任何新策略上线必须走完四阶段（对应死法 20）：
  1. **dryrun**（`run_gate_experiment.sh --mode dryrun`）：不连真实订单，验证逻辑。
  2. **影子模式**：与实盘并行运行，记录虚拟信号但不下单；≥ 2 周，信号与实盘行情对齐度 > 95% 才过关。
  3. **小资金**：≤ 1% 仓位，≥ 1 个月，真实滑点/成本回填到回测引擎。
  4. **正常仓位**：通过 PBO/CPCV + 20 死法评审后放行。
- **回滚成本**：每个版本在 `registry.yaml` 里记录一键回滚点；出问题 5 分钟内能切回上一个版本。
- **为什么反脆弱**：早期失败的代价被压到极低，团队敢试错；试错积累的反馈（真实滑点、断连行为）反过来修正系统——每次失败都让下一次更可靠。

## 四、待验证假设

> 以下防御措施目前是理论推演，**未在实盘验证**。小资金阶段必须逐项确认或证伪。

| # | 假设 | 验证方式 | 通过标准 |
|---|---|---|---|
| H1 | stale 检测阈值设 30 秒合理（死法 13） | 影子模式跑 1 个月，统计 WebSocket 自然断连时长分布 | 99% 断连 < 30 秒 |
| H2 | 缺口清洗阈值（`gap_normalizer.py` 产物）能覆盖真实跳空（死法 4） | 小资金阶段记录所有跳空事件，对照 CLEAN 集标记 | 漏标率 < 5% |
| H3 | 仓位上限按 CLEAN 集最坏回撤估计，不会在 regime 切换时爆（死法 19） | 小资金 6 个月，观察动态 allocator 实际下调仓位频率 | 至少触发 1 次主动降仓且未爆 |
| H4 | 止损放在 ATR 倍数 2.0（来自分布校准）不会被常规插针扫掉（死法 10） | 小资金 100 笔交易，统计止损被扫后 1 小时内回弹比例 | < 30% |
| H5 | WebSocket + OKX 实盘的异步返回检查能 100% 捕捉幽灵订单（死法 11） | 故障注入测试：人工构造 requote / 保证金不足 / 市场关闭 | 0 笔幽灵持仓 |
| H6 | 探索池 10% 仓位的最大回撤可承受（杠铃策略） | 模拟 3 年历史，跑探索池策略组 | 月最大回撤 < 15% |
| H7 | 影子模式 2 周对齐度 > 95% 的门槛足够（死法 20） | 用历史 3 个已知 bug 版本回放 | 全部被对齐度检查拦下 |
| H8 | 容器 NTP 偏移 > 500ms 拒绝启动的阈值（死法 16） | 生产环境采集 1 个月 NTP 偏移分布 | 99% 时间偏移 < 100ms |
| H9 | PBO < 0.3 作为上线门槛（死法 5） | 对历史已爆仓的策略回算 PBO | 爆仓策略 PBO 全部 > 0.3 |
| H10 | 连亏 N 笔熔断的 N 值（死法 17） | 历史 3 年交易流回放 | 熔断触发时平均再亏 < 1R，且无误伤正常策略 |
