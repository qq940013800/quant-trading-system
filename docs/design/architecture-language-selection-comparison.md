# 架构与编程语言选型对比评估（对照「双栈异构架构」分层方案）

> 评估对象：飞书文档附件《11.1 主推荐方案：双栈异构架构》分层选型图（L4/L2/L3/L1/L5 + 基础设施）。
> 方法论：第一性原理拆解各层本质约束 → 对照全球机构可复制实践 → 结合本项目阶段基线裁决。
> 证据等级：**confirmed**（代码/依赖实测）｜**inferred**（由延迟预算与阶段推导）｜**unknown**（未压测/未读到源文档论证）。
> 版本：v1.0（2026-11-08）｜ 状态：设计评估，未改动运行时、配置与实盘资金路径。

## 0. BLUF（裁决先行）

1. **语言由延迟预算驱动，不由性能崇拜或潮流驱动。** 先写清每一环的延迟上限，再选语言；预算没定的选型都是偏好。【inferred，依据 05 篇 §1.1】
2. 截图双栈方案（Python 研究/优化 + Go 风控执行/接入 + Rust 可选 + Java/Go 平台层 + gRPC/Protobuf 契约 + Kafka/NATS + ClickHouse）是一套**规模化、多团队、高吞吐**的目标态架构；其**职责分层划分合理**，但语言栈组合对当前单人/小团队、M5 中频、demo 阶段属于**过早异构**。【inferred】
3. **现阶段裁决：保持 Python 单栈**——`core/` 研究/决策/风控纯函数 + Flask 服务 + 原生 JS 前端 + MQL5 终端执行。只做两件「预留接缝」的事：① 跨层数据契约维护**单一 schema 真相**（Bar / Signal / Decision / OrderRequest）；② 边界只传快照数据、不传计算逻辑。**不提前**引入 Go/Rust/Java 服务、消息队列集群、时序库或 K8s。【confirmed 现状 + inferred 裁决】
4. **触发异构的条件必须是可观测的量化信号**，而非架构偏好：热路径 p99 延迟超预算且 profiler 定位到语言瓶颈；并发连接/吞吐超出 Python 服务能力；需要独立于 Python 进程存活的稳定风控闸；团队规模能承担双栈运维。【inferred】

## 1. 第一性原理：选型的五个本质约束

每一层在选语言/框架前，先回答五个约束；语言是约束的解，不是起点。

| 约束 | 含义 | 冲突时优先级 |
|---|---|---|
| 延迟预算 | 该环允许的时延上限（微秒/毫秒/秒/分钟），由业务频率决定 | 中 |
| 吞吐/并发 | 连接数、消息速率、序列化压力 | 中 |
| 故障安全 | fail-closed、确定性、崩溃后进入已知安全状态 | **最高** |
| 生态可得性 | 该领域成熟库、人才、可复用实现 | 高 |
| 团队/运维成本 | 构建、测试、排障、招人、双栈语义对齐 | 高 |

**约束冲突时的排序**：故障安全 > 可审计 > 延迟 > 开发速度 > 性能极致。【inferred，与蓝图 P6/P8 一致】

### 1.1 本系统延迟预算（M5 中频，引自 05 篇 §1.1）

| 环节 | 合理预算 | 预算超了会怎样 |
|---|---|---|
| 行情落地 → 特征可用 | 秒级（bar 收盘后） | 错过下一 bar 决策，信号退化 |
| 信号生成 | 百毫秒级 | 同上 |
| 风控校验 | 十毫秒级 | 行情跳空时无法拦截 |
| 订单发送 → 回执 | 百毫秒级（零售经纪商） | 滑点扩大，成交价偏离 |
| 审计落盘 | 异步，秒级 | 无（不得阻塞下单） |

上表**没有任何一档需要微秒级**；微秒级只在做市/抢单成立，需要交易所直连与 colocation，零售通道不可达。【行业共识，05 篇 §1.1】

## 2. 双栈方案逐层对照评估

| 层 | 截图选型 | 本质约束 | 全球实践对照 | 合理性判断 | 本项目现阶段匹配度 |
|---|---|---|---|---|---|
| **L4 自动优化层** | Ray Tune / Optuna / RLlib（Python） | 离线/批处理，延迟不敏感；ML/数值生态是硬约束 | 研究台全球共识 Python/R | Python 正确；Ray/RLlib 偏重 | **部分匹配**：Optuna 可用于工程目标；Ray Tune/RLlib 对单机小题是运维负担，且 RLlib 与本系统「不做 DRL 方向预测」边界冲突 |
| **L2 策略计算层** | FastAPI / Ray Serve（Python）；特征计算/模型推理/信号生成 → TradingSignal（gRPC/Protobuf） | 百毫秒级；研究/生产同一份特征代码；可审计 | 研究/在线推理同生态 | Python 足够；FastAPI 异步/类型优于 Flask；Ray Serve 为分布式编排 | **部分匹配**：当前 Flask 无强迁必要；gRPC/Protobuf 契约在单语言阶段可先用内部 schema，预留 IDL 位置 |
| **L3 风控执行层** | go-zero / zrpc（Go）；事前风控/仓位校验/订单编码/路由 → OrderRequest | 十毫秒级、确定性、fail-closed、并发；不被研究层 GC 抖动牵连 | 中低频执行/服务层 Go 增长快；HFT 才需 C++ | Go 作为未来独立风控/执行服务是合理选项 | **暂不匹配**：风控纯函数已在 Python `core/`，适配器尚未接线；无需现在上 Go。Go 的价值是独立进程/并发/单二进制部署，而非语言速度本身 |
| **L1 行情接入层** | go-zero（Go）／必要时 Axum（Rust）；协议适配/tick 解码/归一化/广播 | 高吞吐网络解析、序列化、并发 | Go 生态成熟；Rust 内存安全/接近 C++ 性能 | Go 够用；Rust 仅在解码吞吐/内存安全成瓶颈时考虑 | **暂不匹配**：当前走 ccxt/aiohttp/websocket-client，无独立接入层需求 |
| **L5 平台服务层** | Spring Cloud Alibaba 或 go-zero；账户/持仓/报表/审计/权限 | CRUD/事务/权限，延迟不敏感；生态与团队熟悉度优先 | Java 企业治理成熟；Go 轻量 | 二选一在规模化后成立 | **暂不匹配**：Spring Cloud 是微服务全家桶，单人/单服务阶段过度设计；当前 Flask + PostgreSQL 已覆盖 |
| **基础设施** | Kafka/NATS（事件）· Nacos/Etcd（配置）· K8s（编排）· OpenTelemetry（追踪）· ClickHouse（tick 存储） | 语言无关；按规模引入 | 大厂规模化标配 | 选型方向正确 | **暂不匹配**：当前单机/单进程，Redis + Celery 已够；队列集群、时序库、K8s 属规模化后再引（05 篇 §6：当前规模不该补） |

### 2.1 L4 优化/ML 训练补充
- **Python 是正确选择**：numpy/pandas/scipy/sklearn/GBM 生态与迭代速度无可替代。【行业共识】
- **Ray Tune**：分布式超参编排；单机小题引入即序列化开销 + 调试复杂度（05 篇 §3.2）。
- **RLlib/DRL**：本系统 ML 定位钉死为「L2 状态权重、L3 meta-labeling 过滤、概率→仓位映射」，**ML 不生成方向**；强化学习方向预测明确不做（蓝图 §6、05 篇 §3.3 FinRL 行）。
- **Optuna 纪律**：仅可用于与绩效无关的工程目标（如使推理延迟达标）；任何按绩效目标的搜索都违反「阈值来自分布」与 trials 纪律（05 篇 §3.2、AGENTS 硬规则 11）。

### 2.2 L2 策略计算补充
- **研究/生产同一份特征代码**是硬原则（蓝图 P2、05 篇 §4.5）：隔离的是环境不是逻辑；分两套实现 = 两套 bug。
- **FastAPI vs Flask**：FastAPI 原生异步、类型注解、OpenAPI 自动生成，更贴近在线推理；但同属 Python，迁移不构成新栈。当前 Flask 服务规模小，无强迁理由。【inferred】
- **契约位置**：单语言阶段跨层传 dataclass/类型快照即可；gRPC/Protobuf 作为未来跨语言边界的预留接缝，不在现阶段落地。

### 2.3 L3 风控执行补充
- 风控层的第一要求是 **fail-closed**：风控不可用 = 拒绝交易，不是 fail-open；且 kill switch 必须能在不依赖策略进程存活的情况下生效（05 篇 §4.4）。
- 未来若抽独立风控/执行服务，**首选 Go** 的理由：goroutine 并发模型、静态类型、单二进制部署、易与研究层通过契约解耦；不是因为 Go「比 Python 快」。【inferred】
- 触发前提：现有 Python 风控纯函数已固化并单测，适配器接线完成后，再评估是否需要独立进程隔离。

### 2.4 L1 行情接入补充
- 接入层本质是网络协议适配与归一化，吞吐压力来自连接数与 tick 速率；当前零售通道 + 单标的，无高吞吐解码瓶颈。【inferred】
- Rust(Axum) 仅在未来出现「高吞吐解码 + 内存安全硬要求 + 团队具备 Rust 能力」三者同时成立时再评估；团队无 Rust 经验且交付期紧时不用（05 篇 §2 Rust 行）。

### 2.5 L5 平台服务补充
- 账户/持仓/报表/审计/权限是延迟不敏感的 CRUD 与事务场景；选型优先团队熟悉度与现有生态，而非语言性能。【inferred】
- **Spring Cloud Alibaba** 绑定微服务全家桶（注册/配置/网关/事务），在单服务阶段引入是组织复杂度前置；Go 轻量但当前同样无必要。

## 3. 架构范式对比：单栈分层 vs 双栈异构

### 3.1 职责面 ≠ 实现语言
- 蓝图 §3 按**数据面 / 研究面 / 决策面 / 执行面 / 可观测面 + 控制面**切分职责；截图按**语言栈 + 层**切分。两者不冲突：**先定职责边界与跨层契约，语言是各层的实现选择**。【inferred】

### 3.2 两种形态的代价对照

| 维度 | 单栈分层（当前基线） | 双栈异构（截图目标态） |
|---|---|---|
| 代码同构 | 研究/生产同一份特征代码，无跨语言语义分歧 | 需跨语言对齐指标口径，存在「同一指标两处实现」发散风险 |
| 构建/测试/排障 | 一套运行时、一套测试体系 | 双运行时、双构建、两套监控排障 |
| 故障隔离 | 进程内耦合，需靠模块边界与纯函数隔离 | 热路径可独立部署、独立扩容、故障进程级隔离 |
| 并发模型 | 受单语言运行时约束（Python GIL） | 可按层选并发模型（goroutine/线程/异步） |
| 契约成本 | 内部类型即可 | 需 IDL + 契约测试 + 跨语言数值/时区精度对齐 |
| 适配层厚度 | 薄，退出成本低 | 厚，换语言需重写边界适配 |

### 3.3 不可妥协的范式原则（与语言选型无关）
- **事件驱动为上线依据**，向量化仅作否证：上线结论必须来自事件驱动引擎；向量化模型无法表达部分成交/队列/拒单（05 篇 §4.1）。
- **研究/生产隔离环境不隔离逻辑**：数据源/密钥/下单通道隔离，计算逻辑同一份（05 篇 §4.5）。
- **确定性回放 + 幂等订单 + kill switch 分层**：把不可复现故障变成可复现测试用例（05 篇 §4.2–4.4）。

## 6. 演进路径：预留接缝，不提前建栈

### 阶段 0（当前 P0，能安全地跑）
- **保持 Python 单栈**：`core/` 纯函数 + Flask 服务 + 原生 JS + MQL5 执行。
- 跨层契约用内部类型（dataclass/类型注解）落地；字段定义维护**单一真相源**；边界只传快照数据，不传计算逻辑。
- 验收：研究/生产调用同一特征函数；跨层金额/数量/方向/时间口径一致；纯函数边界可单测。

### 阶段 1（P1，能可信地跑）
- 若服务层需要异步/类型增强，**同语言内**评估 Flask → FastAPI 迁移（不引入新栈）；实验跟踪与注册中心沿用 Python 体系。
- 不引入独立外部语言服务；消息/队列仍用现有 Redis + Celery。

### 阶段 2（规模化触发后，按需抽离）
1. **先抽独立风控/执行服务**：首选 Go（单二进制、goroutine 并发、易部署），通过 gRPC/Protobuf 与研究层通信；两侧跑同一组契约黄金用例。
2. 接入层仅在出现高吞吐解码瓶颈时评估 Rust(Axum)。
3. 平台层继续 Python 或 Go；**不引入 Spring Cloud 全家桶**，除非确实拆分出多个需要独立治理的服务。
4. 中间件按规模补：先事件总线（NATS 轻量优先于 Kafka 重集群），再时序库，最后编排层。

### 阶段 2 的进入条件（须有实测证据）
- profiler 定位到语言/运行时为瓶颈，且 p99 延迟超 §1.1 预算；
- 并发连接/吞吐压测超出当前服务能力；
- 现有 Python 进程内隔离无法满足风控闸独立存活要求；
- 团队具备维护第二语言栈的人力与排障能力。
