# 05｜语言与代码库：选型、复用与架构模式

> L2 综合研究层。本文不重复 L1 `references/dev-practices.md` 与 `system-architecture.md` 的教科书内容，
> 只写**判断**：什么该用、什么该抄、什么必须自研，以及每一条的代价。
> 适用范围：单人/小团队、中低频（日内 M5 及以上）、单一经纪商（MT5）的现实约束。
> 版本：v1.0 ｜ 建立：2026-11-02 ｜ 维护：平台/执行工程

## BLUF（先给结论）

1. **语言选型的唯一驱动是延迟预算，不是性能崇拜。** 先写清每一环的延迟上限（微秒/毫秒/秒/分钟），再选语言；预算没定的选型都是偏好。【推断】
2. **M5 黄金这类中频场景，Python 足以覆盖全链路**（研究 + 回测 + 信号 + 审计），把 C++/Rust 引入热路径在当前是**负收益**：多一套构建、多一处语义分歧、多一个 bug 面。【推断】
3. **"先复用再自研"的判断顺序不是"有没有现成库"，而是**：是否核心差异 → 是否在热路径 → 许可证是否可用 → 维护状态是否可信 → 数据假设是否与本系统一致。任一项否，就只能"参照设计、自己实现"。【行业共识】
4. **回测框架的正确用法是"交叉验证两个独立实现"，不是"信一个框架"**。同一策略在向量化框架与事件驱动引擎上结果差异大的地方，就是你对成本/成交的理解错的地方。【推断】
5. **开源量化框架的公共短板是"数据假设"**：它们假设连续可交易、无跳空、有充足流动性、时间戳干净。本系统的 XAUUSD 数据恰好在这四点上都脏。【推断】
6. **架构模式里最值钱的四个**：确定性回放、幂等订单、kill switch、研究/生产同一份特征代码。它们的共同点是**把不可复现的故障变成可复现的**。
7. **引入任何依赖都要先回答"怎么退出"**：适配层厚度决定退出成本。没有适配层的直接调用，等于把该库的 API 写进了你的业务逻辑。【行业共识】

## 1. 热路径原则

### 1.1 先定延迟预算

| 环节 | 合理预算（中低频） | 预算超了会怎样 |
|---|---|---|
| 行情落地 → 特征可用 | 秒级（bar 收盘后） | 错过下一 bar 决策，信号退化 |
| 信号生成 | 百毫秒级 | 同上 |
| 风控校验 | 十毫秒级 | 行情跳空时无法拦截 |
| 订单发送 → 回执 | 百毫秒级（零售经纪商） | 滑点扩大，成交价偏离 |
| 审计落盘 | 异步，秒级 | 无（不得阻塞下单） |

**判断**：上表没有任何一档需要微秒级。微秒级只在做市/抢单场景成立，而做市需要交易所直连与 colocation，**不是零售 MT5 能触达的门槛**【行业共识】。因此本系统引入 C++/FPGA 的收益为零，成本为正。

### 1.2 热路径的真含义
热路径不是"跑得快的代码"，而是**延迟预算最紧、错误代价最高**的那段。它的设计原则是：
- **不做 I/O**（读盘、查库、打日志全部移出）；
- **不做动态分配**（预分配、对象池）；
- **不做浮点不确定性操作**（禁止依赖哈希顺序、集合遍历顺序）；
- **单一职责**：一个函数只读快照、只写订单意图。

在 Python 里，这四条对应：开跑前把数据全部读入内存、用 `__slots__`/dataclass 预分配、禁止 `set` 遍历参与决策、把下单封装成纯函数。**M5 场景用 Python 满足这四条，比换语言更容易成功。**【推断】

## 2. 语言选型

| 语言 | 定位 | 优势 | 代价 | 何时**不**用 |
|---|---|---|---|---|
| **Python** | 研究/回测/信号/编排 | 生态最全；迭代最快；审计与实验工具成熟 | 解释执行、GIL；类型与性能需自律 | 微秒级热路径；高并发行情分发 |
| **C++** | 执行热路径、低延迟 | 零开销抽象、内存可控、生态成熟 | 开发慢、内存/生命周期 bug 面大、构建复杂 | 策略仍在快速变化期（改一次编译一次） |
| **Rust** | 新执行层/数据面 | 接近 C++ 性能、内存安全、并发安全 | 学习曲线、生态与人才储备弱于 C++ | 团队无 Rust 经验且交付期紧 |
| **Java** | 中后台/风控服务 | 企业级生态、JVM 成熟、人才充足 | GC 抖动（可通过调优/低分配规避）；启动重 | 单机研究工具（Python 更快） |
| **KDB+/q** | Tick 级存储与查询 | 列存 + 向量语言，海量 tick 聚合极快 | 商业许可成本、人才稀缺、生态封闭 | 数据量在单机内存可容纳（pandas/polars 够） |
| **Julia** | 数值原型/研究加速 | 语法接近 Python、性能接近 C | 生态小、包稳定性参差、团队复用难 | 需要与现有 Python 生态深度互操作 |
| **MQL5** | MT5 终端执行 | 与经纪商无缝、内置回测 | 生态封闭、调试弱、测试工具缺失 | 任何"需要被单测覆盖"的逻辑 |
| **Pine** | TradingView 原型/可视化 | 极快验证想法、图表生态 | 无法表达复杂风控；回测引擎黑箱；不可审计 | 任何需要上实盘资金验证的假设 |

**跨语言边界的四条纪律**（一旦引入第二种语言就生效）：
1. **单一 schema 真相**：`Bar`/`Signal`/`Decision` 的字段定义只有一处权威（当前是 `AI_ML_SYSTEM_DESIGN.md` ③），两侧各自生成代码，禁止手抄。
2. **边界只传数据不传逻辑**：跨语言调用只做数据编解码，不做计算分工，否则"同一指标两处实现"必然发散。
3. **契约测试**：边界两侧各跑同一组黄金用例（同输入同输出），任何一侧改字段即失败。
4. **时区与精度显式**：UTC + 整型最小单位（points/ticks），禁止浮点跨边界传递价格。

**关于 MQL5 的定位（重要）**：EA 只做"执行 + 本地校验"（重试、止损单调、规格读取、熔断），**不做策略决策**。
理由是 MQL5 没有可用的单元测试体系，而本系统硬规则 10 要求改动必带单测。【推断】策略逻辑放 Python 的直接后果是：Python 侧挂了，EA 必须能安全地"不动作"（fail-safe）。

**关于 Pine 的定位**：只用于**想法可视化与快速否证**。它的回测引擎不公开成交假设，结论不能作为任何上线依据。

## 3. 开源代码库全景

> **说明**：许可证一列是常见公开信息，用于初筛；**采用前必须读仓库 LICENSE 原文**，本表不构成法律意见。
> 维护状态会变，以仓库最近提交与 issue 响应为准；本文不写版本号，具体版本与 API 以官方文档为准。

### 3.1 数值与数据处理

| 库 | 定位 | 可复用什么 | 坑 |
|---|---|---|---|
| **numpy** | 数值地基 | 向量化、`float64` 语义、`fromiter` 高效转换 | 浮点累积误差（回测权益必须用可控精度的累加）；`np.random` 全局种子污染（用 `default_rng`） |
| **pandas** | 表格时间序列 | `DatetimeIndex` 对齐、resample、rolling | 隐式对齐会**静默**引入未来数据（join 方向错）；`SettingWithCopyWarning`；大表内存膨胀；链式赋值 |
| **polars** | 列式多线程替代 | 惰性执行、内存效率、显式 schema | API 与 pandas 不同（迁移成本）；生态与部分库不兼容（sklearn 需转 numpy）；时间序列 rolling 语义需核对 |
| **numba** | Python 热函数 JIT | `@njit` 加速纯循环（bar 循环、标签生成） | 首次编译延迟；不支持任意 Python 对象；与 pandas 混用需转 numpy；调试体验差 |
| **DuckDB/Parquet**（作存储参照） | 列存 + SQL 查询 | 零运维的本地分析引擎 | 并发写弱；不适合作为在线服务存储 |

**判断**：本系统的 bar 循环与标签生成是 O(n·L) 的纯数值循环，是 numba 的典型适用场景；但**先用 profiler 证明它是瓶颈**，否则引入 JIT 只是增加构建复杂度（L1 `dev-practices.md`「不要过早优化」）。

### 3.2 机器学习

| 库 | 定位 | 可复用什么 | 坑 |
|---|---|---|---|
| **scikit-learn** | 传统 ML 标准库 | `Pipeline`/`TimeSeriesSplit`/校准（`CalibratedClassifierCV`）/指标 | `train_test_split(shuffle=True)` 默认会害人；`Pipeline` 外的预处理会泄漏；`cross_val_score` 对时序无 purge |
| **LightGBM** | GBDT 主力 | 表格特征、early stopping、单调约束 | 小样本易过拟合（`num_leaves` 需压）；类别特征处理与缺失值语义需显式；`predict` 不可外推 |
| **XGBoost** | GBDT 备选 | 稳定性、缺失值原生处理、生态成熟 | 同样不可外推；默认参数在金融小样本上偏复杂；GPU 路径对小题无意义 |
| **CatBoost** | GBDT 备选 | 类别特征与有序 boosting，小数据稳健 | 训练较慢；二进制体积大；调参直觉与 LGBM 不同 |
| **PyTorch** | 深度学习 | 自定义序列模型、可微损失 | 数据饥渴；训练不可复现因素多（cuDNN、并行归约）；**当前阶段禁止引入**（设计文档⑤） |
| **Optuna** | 超参搜索 | TPE/剪枝/试验记录 | **在量化里是 trials 放大器**：任何按绩效目标的搜索都违反"阈值来自分布"；仅可用于与绩效无关的工程目标（如使推理延迟达标） |
| **Ray** | 分布式执行 | 并行回测/并行训练编排 | 单机小题引入即是运维负担；序列化开销；调试复杂 |
| **MLflow** | 实验跟踪 + 模型注册 | 参数/指标/产物版本化、模型 stage 管理 | 服务端组件重（SQLite 后端可轻量）；与 `registry.yaml` 的 trials 纪律需对齐，否则出现两套真相 |
| **ONNX Runtime** | 跨语言推理 | 把 sklearn/GBM/小网络导出为单一推理产物，Python/MQL5 侧行为一致 | 算子覆盖与数值差异需逐模型验证；导出后无法用原库调试；当前 LightGBM 原生推理已足够，**暂无必要** |

#### 3.3.1 NautilusTrader 深入对照（2026-11 复核官方文档）

**定位与形态**【事实·可查证】：开源 production-grade 引擎，核心用 Rust 实现（`crates/`），PyO3 聚合成 `nautilus_trader._libnautilus` 扩展，Python 只做策略逻辑/配置/编排的控制面；也可纯 Rust 写策略。同一 `NautilusKernel` 被三类环境上下文共享：`Backtest`（历史数据 + 模拟执行）、`Sandbox`（实时数据 + 模拟执行）、`Live`（实时数据 + 实盘/纸面账户）。

**核心组件与执行流**【事实·可查证】：
- 组件：`NautilusKernel`（编排/生命周期）、`MessageBus`（pub-sub/请求-响应/命令事件，可挂 Redis 外部后端）、`Cache`（内存订单/持仓/账户/品种，可挂缓存库）、`DataEngine`、`ExecutionEngine`、`RiskEngine`、`Portfolio`、`Trader`。
- 一笔订单：策略 `submit_order` → `RiskEngine` 校验（订单字段、余额、数量、名义价值、reduce-only、交易状态、提交/改单限速）→ 失败返回 `OrderDenied` 且**不到达交易所** → `ExecutionEngine` 路由到对应 `ExecutionClient` → 适配器经 REST/WebSocket 下单 → 回执 `Accepted/Filled/Canceled/Rejected/Expired` 回写 Cache 并触发 Portfolio 与持仓更新；实盘由 `ExecutionManager` 跟踪对账状态、`LiveNode` 做周期检查/截止/取消。
- 线程模型：节点核心**单线程串行**消费消息、跑策略、风控、缓存读写；网络/适配器/日志/持久化在独立 Tokio 后台线程，经通道回灌核心线程。
- 生命周期：组件走有限状态机（`ComponentState` + `ComponentTrigger` 约束合法迁移）；`Actor` trait 负责按 ID 定向消息分发，`Component` trait 负责 start/stop/resume/reset/dispose 生命周期，二者可组合。
- 约束：同一进程内**不支持并发多节点**（日志/时间戳全局态、线程本地运行态非隔离）。

**对照本系统（模块名为本地代码盘点）【推断】**：

| Nautilus 设计 | 本系统对应 | 差距 / 可借鉴点 |
|---|---|---|
| RiskEngine 前置校验：余额、reduce-only、交易状态、限速 | `core/execution/pretrade_gate.py`（数量非负、价格存在、名义价值、总/净敞口、保证金/费用/资金费估算） | 已覆盖数量/名义/敞口/费用；**未显式校验**：账户可用余额是否够保证金+费用、reduce-only 语义、提交/改单限速、熔断/退役状态下是否禁开新仓；这些是 pre-trade 闸可补的校验维度（阈值仍由调用方注入） |
| 三环境共享内核，同一份策略跑 Backtest/Sandbox/Live | `core/backtest/engine.py`（事件驱动回测）+ `core/execution/gate_shadow.py`（shadow 对照） | 已有回测与 shadow 影子期；**缺 Sandbox 中间态**（实时数据 + 模拟执行），介于离线回测与实盘之间；对应设计 4.5「研究/生产同一份代码、隔离的是环境」 |
| ExecutionManager + LiveNode 周期对账 | `core/execution/reconcile.py`（对账底座） | 底座在；周期对账/漂移告警调度接线属阻塞项 #108/#155，未在运行时落地；Nautilus 的「对账状态跟踪 + 截止/取消归属」可作设计参照 |
| 单线程核心串行、IO 后台线程、通道回灌 | 当前 worker/quick_trade 接线 core 闸前的并发边界未定 | 参照点：状态变更串行化可避免竞态；本系统当前规模不必引入消息总线，但并发接线前应明确「谁串行改持仓/谁只产快照」 |
| Actor/Component 状态机与职责分离 | `core/strategies/*`、`core/control/circuit.py`（三态机） | 策略/组件生命周期与消息分发可借鉴「生命周期」与「消息处理」分离；当前单进程内尚不需要独立 Actor 注册表 |

**不引入结论（沿用设计文档⑤）**：只参照上述设计，**不整栈引入**。理由：① LGPL 传染义务与商用闭源边界须法务/人工确认；② Rust/PyO3 构建链与本系统「研究层只依赖 numpy/pandas、可选 sklearn/lightgbm 降级」的最小依赖原则冲突；③ v2 仍 rc、Python 版本要求高于本地 3.12；④ MT5/OKX 适配器需自建，引入后仍要自己写执行适配；⑤ 单标的 M5 阶段，其多 venue/多资产/分布式能力是过度设计。出现「整栈引入」提案即触发人工评审。

### 3.4 组合、统计与优化

| 库 | 定位 | 可复用什么 | 坑 |
|---|---|---|---|
| **statsmodels** | 统计建模与检验 | 回归诊断、ADF/协整、ACF/PACF、稳健标准误 | 大样本慢；部分检验的默认口径需核对（是否含常数、滞后阶选择） |
| **arch** | 波动率与金融计量 | GARCH 族、滚动估计、多步预测 | 参数不稳定（样本短时）；预测区间假设强；作为 ATR 替代需 OOS 验证 |
| **cvxpy** | 凸优化建模 | 组合权重/风险预算约束求解 | 求解器依赖与数值容差；不可行问题报错信息弱；单标的阶段用不上 |
| **PyPortfolioOpt** | 组合优化 | 均值-方差/风险平价/Black-Litterman 的易用封装 | 依赖历史协方差（非平稳）；对估计误差极敏感；单标的阶段不适用 |
| **riskfolio-lib** | 组合优化（更全） | 多种风险度量（CVaR/CDaR）、层级风险平价 | 文档与 API 变动；计算较重；同样依赖协方差估计质量 |
| **skfolio** | scikit-learn 风格组合 | 与 sklearn 一致的 `fit/predict` 组合模型、交叉验证集成 | 较新，生态小；其 CV 需确认是否时序安全 |

**判断**：组合层在当前（单标的 XAUUSD）是**过度设计**。引入组合优化的前提是 ≥3 个低相关策略且各自已有稳定 OOS 记录；否则优化器只是在拟合协方差估计误差。【推断】

### 3.5 高频、执行与协议

| 库 | 定位 | 可复用什么 | 坑 |
|---|---|---|---|
| **hftbacktest** | 高频回测（含队列位置与延迟） | **延迟与队列位置建模**的思路：成交不是"价格触到就成交" | 面向加密/L2 逐笔；数据要求极高；M5 场景相关性弱，仅作方法论参照 |
| **QuickFIX** | FIX 协议引擎 | 会话管理、序号/重传、心跳 | 许可证需核实（GPL 系传闻，商用务必读 LICENSE）；本系统走 MT5 零售通道，**无 FIX 接入点** |

## 4. 架构模式

### 4.1 事件驱动 vs 向量化
- **向量化**：快，适合因子筛选/参数扫描；但它把"成交"抽象成数组运算，无法表达部分成交、队列、拒单。**结论只能用于否证，不能用于上线**。
- **事件驱动**：慢，但能表达因果顺序与状态机。**上线依据必须来自事件驱动引擎**。
- **纪律**：同一策略在两个引擎上的差异必须能被**解释**（成本、成交价、滑点、bar 内顺序），不能"以快的那个为准"。【推断】

### 4.2 确定性回放
要求：给定同一份输入快照 + 同一份配置 + 同一个随机种子，重放必须逐字节一致。
落地要点：① 禁止依赖系统时钟（传入 `as_of`）；② 禁止依赖字典/集合遍历顺序；③ 随机数统一走显式种子；④ 输入是**快照**（含数据版本哈希）而不是"当前数据库"。
**价值**：把"昨晚那笔奇怪成交"从故事变成可复现的测试用例。

### 4.3 幂等订单
- **幂等键**：`signal_id = f"{symbol}_{bar_ts_utc}_{expert}_{dir}"`（本系统已定义）——同一 bar 同一专家同一方向只能下一次单。
- **单调序号**：跨进程传输必须带自增序号，接收端丢弃重复与过期。
- **状态机**：`intent → sent → acked/partial/rejected`，任何状态缺失都要能被对账发现。
- **坑**：重试与幂等是**一对**——没有幂等键的重试只会造成重复下单；有幂等键但没检查回执，会造成"以为失败其实成功"。

### 4.4 Kill switch（分层，且必须有人工通道）
| 层级 | 触发 | 动作 | 恢复 |
|---|---|---|---|
| 策略级 | 滚动 Sharpe/回撤超阈、漂移告警 | 停该策略开新仓，只平仓 | 人工复核后重启 |
| 账户级 | 日权益回撤超阈、连续拒单 | 停全部开仓，强制平仓可选 | 次日或人工 |
| 系统级 | 数据中断、时钟异常、回执丢失 | 停发信号，EA 进入只读 | 人工 |

**三条硬要求**：① 默认**fail-safe**（风控不可用 = 拒绝交易），不是 fail-open；② kill switch 必须能在**不依赖策略进程**的情况下生效（否则策略进程卡死时它一起失效）；③ 每次触发都要落审计（谁、何时、依据什么数值）。

### 4.5 研究/生产隔离（同一份代码，不同环境）
- **同一份特征代码**：研究、回测、实盘调同一个函数，参数来自 config。分两套实现 = 两套 bug。
- **隔离的是环境不是逻辑**：数据源、密钥、下单通道隔离；计算逻辑不隔离。
- **影子期（shadow）**：新版本先只产出 `Decision` 快照而不下单，与线上版本逐笔对比差异。这是唯一能在不冒资金风险的前提下发现"逻辑漂移"的手段。
- **禁止**：研究员在自己机器上"临时改一版"跑实盘。

### 4.6 版本化数据
- **不可变**：原始数据只追加不修改；清洗产物带 `derived_from` 哈希。
- **manifest**：每份数据集有 `(symbol, 时间范围, tz_offset, 生成脚本 commit, 行数, 缺口清单)`。
- **时区是数据的一部分**：DST 切换规则变化时，历史 offset 不得重算（会把已发布结论改掉）。
- **坑**：用"最新复权/最新合约规格"回测历史，是隐性前视偏差的一种。

## 5. 「先复用再自研」决策树

```
需要某个能力
├─ Q1 它是本系统与别人的差异来源吗？（策略逻辑/标签/验证）
│    └─ 是 → 自研（外部库只能做参照）  ← 策略、标签、验证、阈值
├─ Q2 它在该能力的热路径上、且延迟预算 < 1ms 吗？
│    └─ 是 → 谨慎复用（成熟 C++/Rust 库）或自研小核
├─ Q3 许可证是否允许你的分发方式？（GPL 系对闭源不友好；LGPL 有链接义务）
│    └─ 不确定 → 不用（不要用"应该没事"做技术决策）
├─ Q4 维护状态是否可信？（近 12 个月有实质提交 / issue 有回应 / 有测试）
│    └─ 否 → 不用（除非你准备接手维护）
├─ Q5 它的数据假设与本系统一致吗？（连续可交易/无跳空/日频/美股票/加密）
│    └─ 否 → 只参照设计，不引入代码
└─ Q6 总拥有成本 < 自研成本吗？（含适配层、升级、调试、招人）
     └─ 是 → 复用（必须写适配层）；否 → 自研或暂不做
```

配套纪律：
1. **Spike 先行**：2 天内用最小用例验证"能不能跑通我们的脏数据"，跑不通就放弃，不要"再花一周试试"。
2. **适配层强制**：业务代码只依赖自己的接口，库调用集中在 `adapters/`；换库只改一层。
3. **不 fork，除非准备长期维护**：fork 的隐性成本是"永远无法上游合并"。
4. **可退出性**：任何依赖都要能回答"如果明天它停更，我们多久能换掉"。
5. **依赖数量是负债**：每个新增依赖都要在 PR 里写清"为什么不能用已有依赖实现"。本系统的"最小依赖原则"（设计文档⑤）应继续执行。
