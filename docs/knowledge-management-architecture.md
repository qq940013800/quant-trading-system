## 设计哲学

### 第一性原理推导

```
交易系统的本质是什么？
↓
不是一堆策略和代码的集合
↓
而是一个学习系统
↓
它应该从每次交易、每次故障、每次实验中学习
↓
变得越来越聪明，而不是越来越旧
```

### 核心洞察

**知识管理的本质是：把"隐性知识"转化为"显性知识"，把"个人经验"转化为"组织资产"。**

### 全球顶级机构的做法

| 机构 | 知识管理实践 |
|------|-------------|
| **Renaissance** | 每个策略都有完整的"策略笔记"，记录假设、验证、结果、失败原因 |
| **Two Sigma** | Feature Store跨策略复用特征；实验管理系统严格记录每次实验 |
| **Jane Street** | 内部Wiki + Playbook文化；Post-mortem复盘文化 |
| **Bridgewater** | 极度透明的文化，错误要公开讨论；"极度求真"原则 |
| **Citadel** | 策略退役时必须做完整复盘，经验沉淀到知识库 |


### Wiki建设原则

1. **单一事实来源**：每个主题只有一个权威页面
2. **可检索**：按主题分类，标签系统
3. **可维护**：定期更新，过时内容标记
4. **可贡献**：任何人都可以贡献和改进
5. **简单**：不要过度结构化，保持灵活

## Playbook建设

### 什么是Playbook？

Playbook是"怎么做某类事情"的标准化流程和最佳实践集合。

**不是理论，是可执行的操作手册。**

### 核心Playbook清单

#### 1. 策略开发Playbook

```markdown
# 策略开发Playbook

## 第一步：策略假设
- [ ] 这个策略赚的是什么钱？（Alpha四分类）
- [ ] 为什么这个Alpha存在？
- [ ] 为什么这个Alpha没有被套利掉？
- [ ] 这个Alpha什么时候会消失？

## 第二步：数据准备
- [ ] 数据质量检查（缺失值、异常值、复权）
- [ ] 集合分离（训练集/验证集/测试集）
- [ ] 数据快照保存（可复现）

## 第三步：策略原型
- [ ] 先写最简单的版本
- [ ] 代码版本控制
- [ ] 单元测试

## 第四步：回测验证
- [ ] 样本内回测
- [ ] Walk-Forward分析
- [ ] 过拟合检测（PBO/CPCV/Deflated Sharpe）
- [ ] 压力测试
- [ ] 回测真实性检查（滑点、佣金、市场冲击）

## 第五步：小资金测试
- [ ] 模拟盘运行
- [ ] 实盘小仓位测试
- [ ] 对比回测vs实盘
- [ ] 滑点和成交质量检查

## 第六步：上线决策
- [ ] 验证层守门员检查
- [ ] 风控配置确认
- [ ] 监控指标确认
- [ ] 退役预案准备
```

#### 2. 故障排查Playbook

```markdown
# 故障排查Playbook

## 第一步：现象确认
- [ ] 客观描述故障现象
- [ ] 记录错误信息和日志
- [ ] 确认影响范围

## 第二步：复现问题
- [ ] 稳定复现故障
- [ ] 记录复现步骤
- [ ] 确认是代码bug还是逻辑问题

## 第三步：分层诊断
- [ ] Layer 1: 数据层
- [ ] Layer 2: 信号层
- [ ] Layer 3: 风控层
- [ ] Layer 4: 执行层
- [ ] Layer 5: 市场层

## 第四步：根因分析
- [ ] 用"5个为什么"深挖根因
- [ ] 区分直接原因和根本原因
- [ ] 确认修复方案

## 第五步：修复验证
- [ ] 最小修复，一次只改一个变量
- [ ] 验证故障已解决
- [ ] 验证没有引入新问题

## 第六步：复盘沉淀
- [ ] 记录故障知识库
- [ ] 更新Playbook
- [ ] 添加预防措施
```

## 复盘机制

### 复盘的类型

| 类型 | 频率 | 目的 |
|------|------|------|
| **交易复盘** | 每笔大交易后 | 从单笔交易中学习 |
| **周复盘** | 每周 | 回顾一周的交易和系统状态 |
| **月复盘** | 每月 | 评估策略表现和系统健康度 |
| **故障复盘** | 每个故障后 | 从故障中学习，避免重复 |
| **策略退役复盘** | 策略退役时 | 完整总结策略生命周期 |

### 复盘的五个层次

```
Layer 1: 发生了什么？（事实）
Layer 2: 为什么会这样？（原因分析）
Layer 3: 我们学到了什么？（经验提炼）
Layer 4: 下次怎么改进？（行动方案）
Layer 5: 怎么确保不再犯？（机制固化）
```


## 实验管理系统

### 实验管理的原则

1. **假设先行**：先有假设，再做实验
2. **控制变量**：每次只改一个变量
3. **统计显著**：不要被随机波动迷惑
4. **可复现**：每个实验都要能复现
5. **记录失败实验**：失败的实验同样有价值

### 实验记录标准模板

```yaml
experiment_id: EXP-20261025-003
hypothesis: 调整 ATR 止损倍数从 2.0 到 2.5，能提高 Sharpe Ratio

# 实验设计
design:
  control_group: ATR=2.0
  treatment_group: ATR=2.5
  data: 过去3年 BTCUSDT 1h数据
  validation_method: Walk-Forward
  significance_level: 0.05

# 结果
results:
  control:
    sharpe: 1.85
    max_drawdown: 12%
    win_rate: 42%
  treatment:
    sharpe: 1.92
    max_drawdown: 14%
    win_rate: 44%
  statistical_test:
    p_value: 0.08
    significant: false

# 结论
conclusion: ATR=2.5 提高了 Sharpe 但也增加了回撤，统计上不显著

# 决策
decision: 暂不采纳，需要更多数据验证

# 复现
reproducibility:
  data_snapshot: snapshots/data_20261025.parquet
  code_version: git commit abc123
  config: configs/strategy_v2.yaml
```

## 知识复用机制

### 知识检索场景

| 场景 | 检索什么 | 怎么用 |
|------|---------|--------|
| 新故障发生 | 类似历史故障 | 直接套用解决方案 |
| 新策略开发 | 同类策略的Playbook | 复用验证过的流程 |
| 新实验设计 | 相关历史实验 | 避免重复实验 |
| 架构优化 | 类似的架构决策 | 参考ADR |
| 新人上手 | 项目FAQ | 快速了解常见问题 |

### 知识复用的原则

1. **检索优先**：遇到问题先检索知识库，不要从零开始
2. **复用优于重写**：能复用的就不要重新发明
3. **贡献文化**：用完知识后，记得贡献新的知识
4. **持续更新**：知识库要持续更新，保持鲜活

## 工作纪律

- **诚实标注确定度**：区分"实战验证"、"理论推断"、"待验证假设"
- **失败模式优先**：先记录怎么失败的，再记录怎么成功的
- **可复现性**：每个实验都要能复现
- **知识是资产**：每次沉淀的知识都是系统的资产
- **复盘不是形式**：复盘要真正提炼经验，不是走流程
